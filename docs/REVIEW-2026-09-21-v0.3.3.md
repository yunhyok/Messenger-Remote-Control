# v0.3.3 독립 소스 검토 결과 (2026-09-21)

[HANDOFF.md](../HANDOFF.md) §6의 점검 우선순위에 따라 공개 소스만으로 수행한 검토 기록입니다. 파일 범위를 겹치지 않게 나눈 여섯 검토(세션·창 처리 A, 수신 증거 B, 본문·이력·전송 C, Slave·통신 D, 화면 판독·빌드·CI E, UI/UX F)의 지적을 조정자가 소스에서 재확인해 통합했습니다. 행 번호는 v0.3.3 소스(`e31a67c`) 기준입니다.

- **구분:** 확정 = 소스에서 결정적으로 확인된 결함 · 가설 = 실행 환경/현장 조건에 따라 달라지는 지적 · 개선 = 기능/UX 개선 제안
- **처리:** 0.3.4 = 이 검토의 후속 변경에 반영 · 문서 = 코드 변경 없이 기록만 · 보류 = 현장 근거가 있어야 결정

계약(Pending, 정확한 명령 일치, 최신 두 관찰 기반 전송, 모든 부분 완료 후 이력 저장, 8 Mi/32 Mi 한도의 명시적 실패, loopback LM Studio 전용, 대상 창 이동·크기 변경 금지)은 여섯 검토 모두에서 **위반을 찾지 못했습니다.** v0.3.3의 Ready 본문 완화가 명령 변경·삭제·교체·재실행을 허용하는 경로도 발견되지 않았습니다(B 검토, `ReceiveProbe.EvaluateCore`의 `requireVisible` 분기와 `RequireHistoryPrefix`의 행 식별 비교).

**영향:** 중단은 실제 입력 전(`attempted=False`)이므로 메시지가 잘못 전송되거나 초안이 남지는 않았습니다. 그러나 중단이 곧바로 세션을 끝내(`STATUS_REQUEST_STOPPED`) 회신이 가지 않았고, 밤새 대기하던 Master가 아침에 멈춘 채 발견되었습니다. 휴대폰 쪽에서는 명령에 대한 답도, 다음 `Master Ready`도 오지 않습니다. 심각도 P1(운용 정지, 현장 확정).

|---|---|---|
| `watchdog on` | STATUS 목록 조회(`total status`와 같은 질의, Output 수집·Slave 쪽 활성화 없음) 뒤 시작 시각을 읽을 수 있는 PowerSI 전체를 그 시점에 대상으로 고정해 기존 목록에 합칩니다. 같은 PID에 시작 시각이 다르면 새 프로세스로 교체합니다 | `WATCHDOG <코드>` 한 부분: 감시 시작(이미 감시 중인 대상 병기) / 이미 감시 중 / 실행 중인 PowerSI 없음 / Slave 연결 실패(자동 재시도 없음). 다음 확인 시각 포함 |
| `watchdog on <PID>` | 같은 조회 뒤 목록에 있는 그 PID 하나만 추가 | 감시 시작 / 이미 감시 중 / PID 없음 / 실행 중인 PowerSI 없음 / Slave 연결 실패 |
| `watchdog off` | Slave 조회 없이 모두 해제 | 모두 해제 / 감시 대상 없음 |
| `watchdog off <PID>` | Slave 조회 없이 그 PID만 해제 | 하나 해제 / 해당 PID 없음 / 감시 대상 없음 |
| `help watchdog` | 로컬 도움말 | `HELP <코드>` 세 줄 |

문법은 `WatchdogCommand.TryParse`입니다: 정확한 소문자 전체 본문, 단어 사이 ASCII 공백 한 칸, PID는 `[1-9][0-9]{0,9}`이면서 2,147,483,647 이하. 바깥 공백은 기존 `OUTER_SPACES` 규칙대로 제거하고, 대소문자 차이·이중 공백·탭·앞자리 0·부호·비ASCII 숫자·추가 단어는 명령이 아닙니다. `help`처럼 처리 안내와 PC 상태 표본이 없습니다(`RoundTripTest.SamplesPcStatus`). 등록·해제는 전송 완료가 아니라 `ReadOnlyCommands.PrepareWatchdogReply`의 답장 준비 시점에 적용합니다. 목록은 Master 메모리뿐이라 답장이 끊겨도 잃는 자료가 없고, 변경은 운용 창 요약 줄과 `WATCHDOG_COMMAND`에 남습니다. `watchdog on`은 검증(`MachineStatus.Validate`)을 통과한 목록만 등록하며, 예상된 조회 실패는 Slave 연결 실패 답장으로 끝나고 자동 재시도하지 않습니다. 명령어 운용 세션(허브의 "PowerSI 보고서 + 명령어 운용", 기존 M코드 미사용)에서만 동작합니다.

### 흐름

1. **주기:** 허브 화면의 "watchdog 확인 주기"(30분/60분, 기본 30분)는 `%LOCALAPPDATA%\RemoteMonitorMaster\state\master-settings-v1.txt`의 `watchdog_interval_minutes=` 한 줄이며 세션 시작 때 한 번 읽습니다(`WATCHDOG_INTERVAL`). 운용 창이 열려 있는 동안 선택은 비활성이고 바꾼 값은 다음 세션부터 적용됩니다. 다음 확인 시각은 대상별 (마지막 확인 또는 등록 시각 + 주기)의 최솟값이며, 확인 한 번이 모든 대상의 기준을 맞춥니다.
2. **양보:** 확인할 때가 되었거나 재시도 시각이 지난 알림이 있으면, 명령 대기가 idle일 때만 대기 루프 시작점이나 변화 없는 tail 표본 사이에서 대기를 돌려줍니다(`ReceiveProbe.MayYield`: 연속 대기, 명령어 운용, 접수 증거 없음, Ready 뒤 폴링 1회 이상, 재관찰을 기다리는 후보 없음, 화면 밖에 고정된 명령 행 없음, Ready 행 결합). 결과는 증거 없는 `WAIT_YIELDED`이고, `RoundTripTest.Outcome.Yielded`를 받은 `StatusSession.TryReleaseYieldedRequest`가 동의 비트가 하나도 없는 요청만 해제합니다(`STATUS_WAIT_YIELDED`). 완료 회차도 중단도 아니므로 0.3.8의 연속 중단 횟수에 들어가지 않습니다.
3. **확인:** `Run` 안의 `RunWatchdogCheck`가 `pwrsi`와 같은 PowerSI 수집을 한 번 실행합니다. Stop은 이 조회를 취소하고 세션을 끝내며 실패로 세지 않습니다. 조회 실패는 `RecordCheckFailure`가 연속 실패를 세고 모든 대상의 마지막 확인 시각을 갱신하므로 다음 확인은 한 주기 뒤입니다. 성공하면 `WatchdogState.ApplyCheck`가 판정하고 완료·해제 대상을 그 자리에서 목록에서 뺍니다. PowerSI Output 이력은 읽거나 갱신하지 않습니다.
4. **알림:** 완료·해제가 있으면 완료 알림, 경고 조건이 되면 경고를 요청 코드와 같은 할당으로 만든 새 코드에 묶어 큐에 넣습니다(`WATCHDOG_NOTICE_QUEUED`). `SendQueuedNotices`는 부분마다 `Consent.ForWatchdogNotice` → `PrepareSend`(idle 대기·활성화) → `RunBoundObserved`의 새 스냅샷 검사(같은 프로세스, `ValidateContinuity`, 그 알림 코드의 회신 부재, `RequireNoPendingCommand`) 순서로 보내고 `DecideAfterNotice(clean, inputAttempted)`로 정합니다: 깨끗한 전송이고 입력이 있었으면 `SENT`, 둘 다 없으면 `DEFERRED`(큐 유지, 30초·60초·120초… 최대 10분 뒤 재시도, 깨끗한 부분마다 간격 초기화), 그 밖(입력 시도 후 불명확, 모순된 결과)은 `STATUS_WATCHDOG_NOTICE_UNCERTAIN`으로 세션 종료이며 재시도하지 않습니다.
5. **재진입:** 대기 중인 알림이 모두 깨끗이 보내졌고 이번에 한 부분 이상 보냈으면 새 코드의 `Master Ready`를 보내 다음 대기를 그 Ready에 묶습니다. 알림이 없었거나 유예되었으면 같은 코드·같은 Ready 전 기준(baseline)·같은 다음 코드로 대기에 다시 들어가 같은 Ready 행을 다시 결합하고, 그 사이 도착한 명령을 찾습니다. 그래서 확인만 하고 알릴 것이 없으면 휴대폰에는 아무 메시지도 가지 않습니다.
6. **종료:** 세션이 어떤 이유로 끝나든 감시 목록과 보내지 못한 알림을 버리고 `WATCHDOG_CLEARED reason=SESSION_END`(`entries`, `unsent_notice_parts`)를 남깁니다. 감시는 저장하지 않으므로 Master를 다시 시작해도 이어지지 않습니다.

### 판정 규칙

`PowerSiCompletion.Evaluate`는 Output을 한 번 선형으로 읽습니다. 줄 끝은 CR·LF·CRLF이고, 앞뒤 공백을 뺀 256자 이하의 줄 전체가 다음 중 하나일 때만 표시입니다(대소문자 구분, 단어 사이 공백 수는 자유): `AFS Current Frequency ( GHz|MHz ) = <수>`(부호·소수·지수 허용), `AFS Finished`, `Total Sampling Points = <1~18자리 정수>`. 주파수 줄은 실행 중으로, `AFS Finished`는 완료 대기로 바꾸고, Total 줄은 앞선 `AFS Finished`가 연 블록만 완료로 만듭니다(앞선 Finished 없는 Total은 상태를 바꾸지 않음). 따라서 마지막 블록이 결정합니다.

| 조건 (`WatchdogState.ApplyCheck`) | 판정 | 감시 |
|---|---|---|
| 완전한 보고서(`OK`, 부분·누락·읽기 불가 0)에 그 PID가 없거나, 보고서의 시작 시각이 등록 값과 다름 | `MISSING` | 해제. 완료 알림에 "종료되었거나 다시 시작되어 감시를 해제" |
| 불완전한 보고서에 PID 없음, 시작 시각 없음, 상태가 `READ` 아님(Pending 등), 출처가 `BUFFER`/`AUTO_COPY` 아님(OCR 등) | `UNJUDGEABLE` | 유지. 연속 판정 불가 +1 |
| 마지막 `AFS Finished` 뒤에 Total 줄 | `FINISHED` | 해제. 완료 알림에 Total 값과 출처 |
| 마지막 표시가 주파수 줄 | `RUNNING` | 유지. 연속 판정 불가 0 |
| 마지막 `AFS Finished` 뒤에 Total 없음 | `FINISH_PENDING` | 유지. 연속 판정 불가 0 |
| 표시 없음 | `NO_MARKERS` | 유지. 연속 판정 불가 +1 |

경고는 대상의 연속 판정 불가가 정확히 3이 되는 확인에서 한 번(대상별 이유: Pending, 수집 실패, 시간 초과, 수집 안 함, Output 비어 있음, OCR은 판정 안 함, 완료 표시 없음, 보고 없음), Slave 조회 실패는 연속 3회가 되는 확인에서 한 번 보냅니다. 연속 판정 불가는 `RUNNING`/`FINISH_PENDING`에서, 연속 조회 실패는 성공한 확인에서 0으로 돌아갑니다.

알림 머리글은 `WATCHDOG <D코드> | 완료 알림` 또는 `WATCHDOG <D코드> | 경고`이고, 1,400자를 넘으면 `| PART 001/002`처럼 나눕니다. 대상 줄은 "<이름> (PID n): AFS Finished, Total Sampling Points = N (출처: 버퍼|자동 복사)" 또는 "<이름> (PID n): 종료되었거나 다시 시작되어 감시를 해제했습니다", 마지막 줄은 "남은 감시 n개 | 다음 확인 약 HH:mm" 또는 "모든 대상 완료 — watchdog 꺼짐"/"남은 감시 없음 — watchdog 꺼짐"입니다. 이름의 제어 문자는 공백으로 바꾸고, Total 값 외의 Output 본문은 알림에 넣지 않습니다.

### 보호 장치

- **판정 출처:** `PowerSiCompletion.IsJudgeableSource`는 정확히 `BUFFER`와 `AUTO_COPY`만 허용합니다. OCR·LLM·화면 본문은 데이터이며 완료 근거가 아닙니다. CPU·경과 시간·프로세스 존재도 근거가 아닙니다.
- **Output 이력:** 확인은 `PowerSiOutputHistory`를 읽거나 쓰지 않으므로 다음 `pwrsi`의 전체/추가분 기준이 바뀌지 않습니다.
- **대기 양보:** idle 상태에서만 일어나며, 후보가 생긴 대기는 항상 재관찰을 먼저 끝냅니다. 화면 밖에 고정된 명령 행은 회차와 양보를 모두 막고, 다른 행이 대신 접수되지 않습니다(접수 규칙 불변).
- **알림 동의:** `ForWatchdogNotice`는 머리글이 `WATCHDOG <자기 코드> | `로 시작하고 본문이 비어 있지 않은 1,400자 이하 문구만 받으며, 정확한 본문에 1회만 쓰입니다. 알림 동의에는 감시 목록을 붙일 수 없고, 기존 `ForNotice`는 watchdog 문구를 거절합니다.
- **명령 우선:** `RequireNoPendingCommand`는 현재 Ready 전 기준으로 Ready 행을 다시 결합해(`WATCHDOG_NOTICE_BASELINE_REQUIRED`, `WATCHDOG_NOTICE_READY_NOT_BOUND`) 그 뒤에 보이는 명령이나 화면 밖에 고정된 명령이 있으면 `WATCHDOG_NOTICE_COMMAND_PENDING`으로 입력 전에 거절합니다. 확인 중 도착한 명령은 알림보다 먼저 답합니다. 앞서 보낸 알림 행은 명령이 아닙니다.
- **재전송 없음:** 부분은 순서대로 보내고 깨끗이 보낸 부분은 다시 보내지 않습니다. 유예는 입력이 전혀 없었던 경우뿐이며, 입력이 시도된 뒤의 불명확은 세션을 끝냅니다. 큐의 문구는 이후 `watchdog off`가 있어도 준비된 그대로 보냅니다(이미 일어난 확인의 결과이기 때문).
- **기록:** 모든 `WATCHDOG_*` 기록은 PID·시작 시각·상태·출처·길이·횟수만 남기고 프로세스 이름과 Output 본문을 남기지 않습니다. 조회 실패는 예외 형식 이름만, 휴대폰 경고의 이유는 코드(`CheckFailureCode`)만 씁니다.
- **설정 파일:** `WatchdogSettings.LoadIntervalMinutes`는 예외를 내지 않고(파일 없음·64 KiB 초과·해독 불가·잘못된 줄이면 30분, 유효한 줄이 여럿이면 마지막 줄), `SaveIntervalMinutes`는 임시 파일 뒤 교체로 원자적으로 쓰며 다른 줄을 보존하고 해독할 수 없는 파일은 덮어쓰지 않습니다.

### 자체 검사

- `PowerSiCompletion.RunSelfTest`: 예시 Output(주파수 11줄 → `AFS Finished` → Total 118), MHz 실행 중, 완료 뒤 새 주파수(`NEW_SWEEP_AFTER_FINISH`), Total 없는 Finished, Finished보다 앞선 Total, 마지막 Finished 결정, Total만 있는 경우, 대소문자·접두어·마침표·단위·부호 등이 다른 유사 문구 거절, 18자리 한도와 넘침, 숫자 형식, 공백 변형, CR/LF/CRLF 혼합, 빈 입력, 8 Mi 문자 입력 30초 이내, 판정 출처 표.
- `WatchdogCommand`·`WatchdogSettings`·`WatchdogState`·`WatchdogText`(`WatchdogSelfTest`로 묶음): 명령 허용·거절 사례, 설정 파일의 기본값·저장·잘못된 줄·보존·원자적 교체·해독 불가 보호, 등록 병합·재시작 교체·첫 확인 시각·Pending/OCR 미판정·연속 경고 1회·실패 뒤 한 주기 대기·불완전 보고서 유지·모두 완료 시 꺼짐·세션 종료 초기화·60분과 주기 변경, 답장·도움말·알림 문구, 긴 이름 128개 대상의 1,400자 이하 PART 분할과 목록 축약, `IsNotice` 머리글 식별.
- 기존 클래스: `ReceiveProbe`(`MayYield` 256조합 중 idle 1조합만 허용, 알림 행 0~2개 뒤 같은 기준 재결합, 알림 행 뒤 명령 접수, 화면 밖 명령은 양보도 막음, Ready 행 없음·중복·재사용 행·결합된 기준 거절), `RoundTripTest`(`Outcome.Yielded` 조건, watchdog 명령의 처리 안내·PC 상태 표본 없음), `StatusSession`(`DecideAfterNotice` 4조합, 30초→10분 간격, `CheckFailureCode`, 손대지 않은 양보만 1회 해제, 재진입의 같은 코드·새 동의, `RequireNoPendingCommand`, 실제 알림 부분의 1회 동의), `SupervisedSendTest`(새 Ready 문구 128자 이내·명령 아님, 알림 동의의 정확 일치·불일치 시 소모·1회·취소, 잘못된 머리글·다른 코드·길이 초과 거절), `ReadOnlyCommands`(이름 형식 `EXACT`/`OUTER_SPACES`/`CASE_MISMATCH`, `help watchdog` 세 줄과 `help` 목록, 답장 형식과 변조 거절, 가짜 조회로 등록·이미 감시·PID 없음·PowerSI 없음·조회 실패·잘못된 목록 미등록, `watchdog off`의 조회 없음, 명령마다 이름·본문 없는 `WATCHDOG_COMMAND` 1행), `MasterHubForm`(Windows 전용: 주기 선택, 요약 줄이 상태 줄·회차를 바꾸지 않음, 새 단계 문구, 종료 사유 설명, loopback `watchdog on`/`off`).

### 잔여 위험 (설계상, 현장 미확인)

중요도는 결함이 아니라 남는 위험의 추정입니다.

| ID | 위험 | 영향 | 중요도(추정) | 탐지·대응 |
|---|---|---|---|---|
| W1 | 무인 주기 수집이 직접 버퍼 읽기에 실패하면 `pwrsi`와 같이 Slave에서 PowerSI 창 활성화와 자동 복사(포커스·클립보드)를 씁니다. Slave에는 사용자가 작업 중인지 보는 보호가 없습니다 | Slave PC 사용자의 입력·클립보드 방해 | P2 | `WATCHDOG_TARGET_EVALUATED source=AUTO_COPY`. Slave PC를 쓰는 동안에는 감시를 끔 |
| W2 | 확인 중(`pwrsi` 수집, 최대 약 2분)에는 수신 확인을 쉬므로 그 사이 보낸 명령은 확인이 끝난 뒤 처리됩니다 | 명령 응답 지연 | P3 | 운용 창 `WATCHDOG_CHECKING`. 명령 자체는 사라지지 않음 |
| W3 | 명령 행이 화면 밖에 고정된 동안에는 `MayYield`가 거짓이라 확인과 알림도 미뤄집니다 | 완료 알림 지연 | P3 | 운용 창 `COMMAND_NOT_VISIBLE`. 스크롤로 해소 |
| W4 | 각 알림은 실제 Win7 UI 전송이라 idle 대기(최대 60초, 넘으면 유예)를 거치고, 입력 뒤 불명확하면 세션이 끝나 감시와 남은 알림이 모두 사라집니다. 여러 부분 알림이 중간에 유예되면 새 Ready 전까지 일부만 보인 상태가 이어질 수 있습니다 | 운용 정지, 부분 알림 | P2 | `WATCHDOG_NOTICE_DEFERRED`, `STATUS_WATCHDOG_NOTICE_UNCERTAIN` |
| W5 | 완료·해제 대상은 판정 시점에 목록에서 빠지며 알림 전송 확인을 기다리지 않습니다. 알림 전에 세션이 끝나면 그 완료는 다시 알리지 않습니다 | 완료 알림 유실 | P2 | `WATCHDOG_CLEARED unsent_notice_parts>0` |
| W6 | 판정은 마지막 블록만 봅니다. 같은 PowerSI에서 새 실행이 첫 주파수 줄을 출력하기 전에는 직전 실행의 완료 블록이 완료로 보이고, 등록 전에 이미 끝난 실행도 첫 확인에서 완료로 알립니다 | 거짓 완료 알림 | P3 | 알림의 Total 값과 시각으로 사용자가 구분 |
| W7 | 표시 형식은 자체 검사의 예시 기준이며 실제 PowerSI Output에서 확인하지 않았습니다. 형식이 다르면 완료를 찾지 못합니다 | 완료 알림 없음(3회 뒤 `완료 표시 없음` 경고) 또는 `FINISH_PENDING` 고착 | P2 | `WATCHDOG_TARGET_EVALUATED outcome=NO_MARKERS`/`FINISH_PENDING` |
| W8 | STATUS 목록은 128개로 제한되어 그 밖의 PowerSI는 등록 시점에 없는 것으로 보입니다(수집 보고서의 누락은 감시 유지로 안전하게 처리) | 등록 누락, `PID 없음` 답장 | P3 | `total status`의 누락 수 |
| W9 | 감시는 세션과 함께 끝나며(Stop·잠금·절전·세션 종료 오류) 휴대폰에는 종료가 알려지지 않습니다. Master를 다시 시작하면 다시 등록해야 합니다 | 사용자가 감시 중이라고 오인 | P2 | 운용 창 "세션 종료 — 감시 없음", `WATCHDOG_CLEARED` |
| W10 | 등록·해제는 답장 준비 시점에 적용되므로 답장이 입력 전에 중단되어 새 Ready로 재개되면 휴대폰은 답장 없이도 감시가 켜진 상태가 됩니다 | 상태 인식 차이 | P3 | 운용 창 요약 줄, `WATCHDOG_COMMAND` |

### 회귀 검사

1. Linux에서 net48 참조 어셈블리로 두 프로젝트 컴파일(경고 0, 오류 0).
2. Mono로 클래스별 자체 검사 개별 실행: 통과 21건·실패 12건. 새 통과 6건은 watchdog 순수 검사(`PowerSiCompletion`과 `Watchdog.cs`의 검사 클래스)이고, 실패 12건은 종전처럼 Windows API·UIA·WinForms가 필요한 단위입니다.
3. 새 단언은 위 **자체 검사** 목록과 같습니다. `MasterHubForm`의 화면·loopback 검사와 실제 EXE `--self-test` 전체는 Windows에서만 실행됩니다.
4. Windows Release 빌드, 두 실제 EXE `--self-test`, 설치파일 생성·자산 검사, 두 역할 설치/재설치/제거/설정 보존 검사는 CI(Windows Server 2025)에서 수행하며 결과는 HANDOFF §9 기록 시 갱신합니다.
5. 현장: 실행 중인 PowerSI로 `help watchdog` → `watchdog on` → 주기 대기 → 완료 알림과 새 `Master Ready` → `watchdog off`를 확인하고, 로그의 `WATCHDOG_COMMAND` 결과, `STATUS_WAIT_YIELDED` 간격, `WATCHDOG_CHECK_RESULT`·`WATCHDOG_TARGET_EVALUATED`의 판정과 출처, `WATCHDOG_NOTICE_SENT`/`WATCHDOG_NOTICE_DEFERRED`, `STATUS_WATCHDOG_NOTICE_UNCERTAIN` 부재를 봅니다([WIN7-TEST.md](../WIN7-TEST.md)). **이 확인 전까지 watchdog의 현장 동작은 주장하지 않습니다.**
